# 百万级搜索审计（v0.1.1 前）

## 复现

```bash
# 现有真实索引：只读打开主库，TEMP 使用独立连接，不访问搜索结果目标。
cargo run --release --example bench_search -- /path/to/index.sqlite

# 直接生成合成 SQLite 测试库，不扫描磁盘、不生成 EFU，不覆盖已有文件。
cargo run --release --no-default-features --example bench_search -- \
  --generate 100000 target/bench-100k.sqlite
cargo run --release --no-default-features --example bench_search -- \
  --generate 500000 target/bench-500k.sqlite
cargo run --release --no-default-features --example bench_search -- \
  --generate 1000000 target/bench-1m.sqlite
```

真实 EFU 可先通过 `examples/check_index.rs` 构建指定测试缓存，再运行本工具。
合成库固定使用 schema 2，含实际生产排序索引及 trigram FTS5。5% 目录，
其余 MKV/TXT；名称交替 alpha/中文/の/beta，编号及路径形成宽泛匹配。
这些是测试记录，不是可供应用监视的真实 EFU 缓存。生成期间中断的测试库应换新路径重建。

`prepare_ms` 是整个 prepare_search；`matches_ms` 包含单条 INSERT 的扫描、
排序及 TEMP 写入；`first_page_read_ms` 仅测准备后的第一页读取；
`first_result_ms` = prepare + 第一页读取，不含输入防抖、worker 调度及 GTK 绘制。
深页读末尾 128 条，使用 position 主键范围，不使用 OFFSET。
TEMP 大小是 page_count × page_size（连接高水位，含可复用空闲页），不是实际写盘量；
RSS 是 benchmark 进程瞬时值，不含 GTK 或内核页缓存。
排序期间短命的 scratch 文件及瞬时 RSS 峰值不由这些快照完整统计。

取消分别在 10ms、基准查询耗时的 50% 和 90% 发起，每阶段 20 次；
只统计真正返回 SQLITE_INTERRUPT 的样本，提前完成不冒充取消成功。
时间起点是发布新 generation，终点是 prepare_search 返回（包括 SQLite 回滚）。
阶段按墙钟延迟近似，不保证每次处于相同 SQLite opcode。
此工具手工运行，不给普通 CI 增加耗时断言。

## 实际发现及修改

1. TEMP DDL 失败可留下旧 matches；原底层 search_page 没有有效性检查。
   现用一个 matches_ready 标志，开始准备时失效，INSERT 成功后才有效。
2. 未准备完成/失败后的分页请求被误当作缓存损坏并触发重建。
   worker 现在丢弃这种请求，仍保持 generation 前后检查。
3. UI 在新查询等待期间保留旧列表，但按当前输入把它标成“全部匹配”。
   搜索反馈与索引状态分离，显示正在搜索及“列表仍为上一次结果”，完成后替换 model；
   周期索引状态/分页通知不再覆盖搜索中或错误反馈。
4. 第一页既随 Results 提供，也可能由 model 懒加载请求重复返回，
   页缓存队列重复 offset 会提前驱逐仍在缓存的页；现在每个 offset 只记一次。
5. 等待 EFU 稳定期间检查间隔缩为 1 秒，完成或失败后恢复 poll_seconds。
   仍要求连续两次相同 stamp，仍使用轮询，没有 inotify。
6. 搜索分页原有快照保护，但浏览分页会在 revision 变化后为旧 generation 重开
   新 inode。现在浏览/搜索均记录连接快照 generation，旧页面继续使用旧连接，
   新 generation 才采用新 revision；回归测试覆盖两种模式。

## 验证的安全边界（没有重写）

- TEMP 只存 position 和 entry_id，不存完整 Entry。
- SQLite 单条 INSERT 有隐式 statement transaction：插入至少 512 个 ID 后
  由钩子触发中断，实测所有 ID 回滚为 0；没有叠加额外事务机制。
- TEMP 配额不足（SQLITE_FULL）也回滚；解除配额后同一连接再次准备成功。
- 新查询失败既不能读取半成品，也不能读取 DDL 失败残留的旧 ID。
- count、第一页及深页共用连接/inode；原子替换后旧 generation 的页继续来自旧库，
  新查询按 revision 重开连接。已有前后 generation 检查保留，UI 也再次过滤。
  浏览分页也固定已建立的连接快照（第一笔成功读取起）。
- Linux 上实际 FILE TEMP fd 是已 unlink 的 etilqs 文件；测试强制落盘，
  SIGKILL 自建子进程后私有临时目录仍为空，不依赖 Rust Drop。
  这不代表索引构建用的 build-*.sqlite 也有相同生命周期（见 README 既有限制）。
- LIKE fallback、默认相关性排序和 TEMP 落盘确实是主要成本，但本机百万条
  仍是亚秒级；没有加 extension 索引、改变 SQL、引入自制搜索或增加排序缓存。

## 测试

新增/扩充确定性测试涵盖：

- a → ab → abc → ab → a、清空、ext:mkv、path:Anime 的部分插入取消；
  名称/大小/修改时间排序均执行取消后恢复（SQLite 写入钩子，不靠 sleep 猜进度）。
- generation 在实际插入途中变化，旧准备被 progress_handler 中断，新准备成功。
- TEMP DDL 失败留下旧表但不能分页；恢复后再次搜索；ID-only schema 和主键页读取计划。
- TEMP SQLITE_FULL 回滚和同一连接恢复；真实落盘 TEMP 的异常退出清理。
- 快速输入/排序队列和旧分页请求丢弃，最终结果及深页正确；实际清空再过滤。
- worker 搜索错误后缓存修复，无需重启；revision 更新后旧页/新查询的 inode 一致性。
- 原有离线缓存、EFU 连续写入/异常行和原子重建失败保留缓存测试继续通过。
- 页缓存重复 offset 去重；Xvfb GUI 测试加入旧行保留、正在搜索反馈验证。

验收命令：fmt --check、严格 all-targets/all-features Clippy、cargo test、
无默认特性测试、启用 EFUSEEK_GUI_TEST 的 Xvfb GTK 测试及 gui-smoke.sh。
没有修改版本、tag 或 Release。

## v0.1.1 前仍值得验证

- 用用户的真实 82 万～100 万 EFU、长路径和真实扩展名分布复跑；
  本报告不是 NAS 冷缓存/慢盘或桌面完整输入到绘制延迟保证。
- worker 空闲时最多等待 100ms，另有配置的防抖及 16ms GTK 事件轮询；
  SQLite 取消延迟不等于新搜索首屏延迟。
- generation/progress_handler 无法中断阻塞中的系统文件 I/O；真实 NAS 挂载
  的不可达/卡住行为这里只用源文件不可访问模拟，没有断开用户网络。
- 连续两次相同 mtime/size 是稳定启发式，不是“生成完成”协议；写入端若暂停
  超过稳定窗口，合法但不完整 EFU 仍可能被接受。建议生成端临时文件 + 原子替换。
- 同 mtime/size 的内容变化仍不可识别；不为理论情况改 SourceStamp/架构。
- 实际 SQLite 页面损坏由既有错误路径关闭连接并请求修复；本轮测试的
  损坏缓存/恢复不覆盖所有损坏模式。非损坏资源错误仍可能请求重建，后续可更细分类。
- 浏览快照从第一笔成功页读取起固定；进一步可验证更新恰好发生在 UI 收到
  count 状态和首次浏览请求之间的边界，避免把它与已准备搜索的完整快照保证混为一谈。
